# Production Supabase audit — demo migration (READ-ONLY, 2026-11-02)

Source: owner-run queries from `01_migration_audit.sql` on project `jecgmiuypuathhvjuhea`. No production change was made.

## 1. Migration history: production ≠ repository filenames

Production records **32** versions; the repository has **30** prior files + the new demo file. Only **15** versions
match by number. The other 17 production versions (`20260717191147` … `20260810014657`) carry timestamps assigned
by the Supabase MCP at apply time, while the matching repo files use hand-written versions
(`20260731090000`, `20260801120000` … `20260810020000`). The 32 vs 30 count difference means two production
entries have no single repo counterpart (most likely a repo file applied as two MCP steps, or a hotfix applied
through the MCP and folded into a later file). Mapping by *name* needs
`select version, name from supabase_migrations.schema_migrations` (names were not exported).

**Consequence:** `supabase db push` would consider 16 repo files "unapplied" and try to replay them.
**It must not be used.** The schema is already in its final state (demo objects absent, everything else present);
only the history table disagrees with the filenames.

## 2. Can the demo migration be applied on its own? Yes.

Objects it depends on, all present in production per the recorded history:

| Dependency | Where it comes from | Status |
|---|---|---|
| schema `private` | `20260716211508_extensions_and_helpers.sql` (`create schema if not exists private`) — production records `20260716211508` | present |
| `auth.users`, `auth.uid()` | Supabase built-ins | present |
| `pg_cron` | optional (see §3) | **absent** |

Everything else the file touches it creates itself (`public.demo_sessions`, `public.demo_session_status()`,
`public.paax_pre_request()`, `private.demo_cleanup()`, the role setting). The social-RPC names inside the guard are
request-path string matches; they do not require those RPCs to exist. No existing table, policy, function or RPC
is altered. Owner-confirmed pre-state: table absent, three functions absent, no pre-request hook configured on
`authenticator`. The file is therefore independent of the 16 unapplied-by-name repo files.

## 3. pg_cron is not installed — cleanup of abandoned demo identities

The migration tries `create extension if not exists pg_cron` inside a `begin … exception` block and only schedules
the sweeper if that succeeds. On Supabase the `postgres` role **can** enable `pg_cron`, so running the file as-is
**would enable an extension** — which the owner has ruled out for now. Two options:

- **A (recommended, needs a one-line approval):** allow `pg_cron` (Supabase-managed, used only for a 1-minute
  `select private.demo_cleanup();`). Cleanup is then independent of traffic. Rollback step `cron.unschedule` applies.
- **B (no extension):** apply the file **without** its final `do $$ … $$` block. Cleanup then relies on the
  paax-api backstop: `sweep_expired()` runs on every `POST /v2/demo/sessions` (grace 60 s, 20 identities per
  call). Expired identities are harmless while they linger (the guard answers 401 to every request; the JWT dies
  within 1 h), but with zero traffic they are only removed when the next visitor arrives. If B is chosen and a
  traffic-independent sweep is still wanted, the smallest addition is a periodic task inside paax-api
  (asyncio timer every few minutes calling the same `sweep_expired`); not implemented, awaits a decision.

Either way `private.demo_cleanup()` is created and can be run by hand at any time: `select private.demo_cleanup(0, 1000);`.

## 4. Compatibility, backup, rollback

- **Guard safety for real users:** returns immediately unless the JWT carries `app_metadata.paax_demo = 'true'`
  (anon, service role and all 5 real users are untouched); claim parsing is exception-wrapped; the only raises are
  the intentional PT401/PT403 for demo identities. Verified on the local stack (same Postgres 17 / PostgREST v16
  majors) with a real signup/login and reads/writes through RLS.
- **`alter role authenticator set pgrst.db_pre_request`:** standard Supabase/PostgREST mechanism, verified locally
  only. If production refuses it (privilege), the transaction below rolls everything back and nothing is attached.
- **Atomicity:** run the file inside one transaction (`begin; … commit;`). `create table/function`, `alter role`,
  `notify` and `create extension` are all transactional in Postgres, so a failure anywhere leaves production exactly
  as it is now.
- **Backup:** take a Dashboard → Database → Backups snapshot immediately before applying. Baseline to re-check after
  any rollback: `auth.users` 5, `public.profiles` 5, `public.playlists` 30.
- **Rollback:** `03_rollback_demo_guard.sql`. Step 1 (`alter role authenticator reset pgrst.db_pre_request;
  notify pgrst, 'reload config';`) removes every request-path effect within one config reload; the rest removes
  the objects and any demo identities. Tested locally.
- **History hygiene (optional, after a successful apply):** record the file so a future audit matches:
  `insert into supabase_migrations.schema_migrations(version, name) values ('20261030000000','demo_sessions');`
  (the MCP `apply_migration` tool does this automatically; the SQL editor does not).

## 5. Recommended procedure (nothing below has been run)

1. Owner decision on §3: A (allow `pg_cron`) or B (strip the `do $$ … $$` block).
2. Backup snapshot.
3. In the SQL editor, run the migration file (full for A, truncated for B) wrapped in `begin; … commit;` —
   or, with the Supabase MCP reconnected, `apply_migration` named `demo_sessions` with the same content.
4. Run `02_post_apply_checks.sql`: role config shows `pgrst.db_pre_request=public.paax_pre_request`
   (and, for A, `cron.job` lists `paax_demo_cleanup`); table and functions exist; `demo_sessions` has 0 rows.
5. Functional checks from a device: existing account login, Home, Library, one playlist; one throwaway
   registration; anon read `rest/v1/genres` with the publishable key → 200.
6. Report; only then proceed to the Cloudflare Pages stage. `DEMO_ENABLED` stays unset until stage 7.

## Addendum (same day) — name-level history mapping and Option A review

**History, by name:** 30 of the 32 production entries match a repository file by *name* (every one of the 30 repo
files is accounted for; only the version numbers differ for 17 of them because the MCP assigned apply-time
timestamps). The 2 production-only entries are `20260717191147 profiles_add_first_last_name` and
`20260717191455 username_available_rpc` (Phase 3.1, 2026-07-17): they exist in production but have **no repo
file** (`first_name` / `username_available` appear in no migration file). The app uses them (see the grep in the
release session), so this is a pre-existing documentation gap, not a schema problem, and not a blocker. It is
listed for a separate review; the demo release does not touch it. Decision: owner chose **Option A (pg_cron)**.

**Cleanup can never delete a real account — three independent conditions must all hold for a row to be deleted:**
1. the id is in `public.demo_sessions` (rows are only ever written by paax-api with the service role; `anon` has no
   privilege, `authenticated` has SELECT only — a real user cannot insert one for themselves or anyone else);
2. that session is expired (past `expires_at` + grace) or explicitly ended;
3. `auth.users.raw_app_meta_data->>'paax_demo' = 'true'` — `app_metadata` is writable only by the service role,
   never by the client SDK (GoTrue rejects user-side edits of `app_metadata`).
The function is `security definer`, owned by `postgres`, EXECUTE revoked from `public`, `anon` and
`authenticated`; it is callable by `postgres` (pg_cron runs the job as the scheduling role, `postgres`) and by
nobody through the API. paax-api's own sweep does not use it; it deletes through the GoTrue admin API after the
same `paax_demo` check. The 5 real users carry no `paax_demo` flag (preflight F confirms `demo_users = 0`).

**Guard, effective configuration and rollback:** `alter role authenticator set pgrst.db_pre_request =
'public.paax_pre_request'` is the PostgREST-documented switch; PostgREST re-reads role settings on
`notify pgrst, 'reload config'` and applies the hook to every request made through the `authenticator` role
(i.e. all REST/RPC traffic; the service-role gateway in paax-api also passes through it and returns at the first
`if`). The function has EXECUTE for `anon`, `authenticated`, `service_role` because PostgREST calls it as the
request role; it runs with `security definer` + empty `search_path`, so it can read `public.demo_sessions`
regardless of the caller's privileges without exposing anything else. Emergency rollback =
`05_emergency_detach_guard.sql` (reset + reload, seconds). Note: the earlier owner query on `pg_roles` returned
zero rows only because of the filter used; `pg_roles` is readable by every role, and preflight D re-queries it.

## Fail-closed verification (staging, 2026-11-03)

Owner requirement: the migration must never commit demo infrastructure without its cleanup job. The final
block was rewritten: `create extension if not exists pg_cron with schema pg_catalog;` as a plain statement (the
former `exception … raise notice … return` wrapper is gone), then `cron.schedule(...)`, then an explicit assertion
that re-reads `cron.job` for an **active** `paax_demo_cleanup` job with the exact command, raising otherwise.
Applied as `postgres` (same role as the production SQL editor; not a superuser on Supabase) via
`04_apply_option_a.sql` on the local stack reset to production's pre-state (no table, no functions, no pg_cron,
no hook). Script: `staging/run_fail_closed_tests.sh`.

| Test | Fault injected | Result | State afterwards |
|---|---|---|---|
| 2 | pg_cron removed from `shared_preload_libraries` (container restarted) | `ERROR: pg_cron can only be loaded via shared_preload_libraries` at the `create extension` line | table absent, 0 functions, extension absent, hook off — **unchanged** |
| 3 | pg_cron installed, `cron.schedule(text,text,text)` renamed away | `ERROR: function cron.schedule(unknown, unknown, unknown) does not exist` | table absent, 0 functions, no jobs, hook off — **unchanged** (pre-installed extension stays) |
| 3b | `cron.schedule` replaced by a stub returning an id without creating a job | `ERROR: paax_demo_cleanup job was not scheduled; aborting the demo migration` (the explicit assertion) | **unchanged** |
| 1 | none | applies | table, 3 functions, pg_cron, `paax_demo_cleanup:true`, hook on |

**Job executes, and only deletes demo identities** (`staging/seed_expired_demo_identity.sql`): one expired
identity with `paax_demo=true` and one flag-less user with an equally expired `demo_sessions` row were inserted;
within the next minute `cron.job_run_details` shows `succeeded`, the flagged identity and its session row are
gone, the flag-less user remains (its stale `demo_sessions` row remains too, harmless, and is impossible in
production because only paax-api writes that table for flagged users). Repeated on the fresh apply after the
failure tests with the same outcome.

Staging-harness note (not a migration issue): the first fault-injection attempt wrote
`shared_preload_libraries` as one quoted string and the local DB container crash-looped until the line was
removed from `postgresql.auto.conf` via a throwaway Alpine container. The script now passes the list unquoted.
This can only happen with `ALTER SYSTEM`, which the release never runs.

**Backup restorability (staging, 2026-11-03, `staging/run_backup_restore_test.sh`):** the local stack was seeded
with two users (identities, a session, a refresh token) and two playlists, dumped with the exact CLI commands of
`00_backup_free_plan.md` (roles, public/private schema, auth+storage schema, all data), restored into an empty
`template0` database, and compared with `06_backup_fingerprint.sql`: **identical**, including md5 over
`auth.users` ids + emails + password hashes + app metadata, `auth.identities`, `auth.sessions`,
`auth.refresh_tokens` tokens, profiles, playlists, catalog ids and `storage.objects` names, plus exact per-table
counts for every table in public/private/auth/storage (Supabase bookkeeping tables excluded). Finding folded into
the procedure: the CLI's plain `--data-only` dump already contains the auth and storage rows, so `data.sql` is
restored once and the per-schema files are kept only as spare copies.

**Transactional behaviour of `04_apply_option_a.sql`:** `create table/function/policy`, `grant/revoke`,
`alter role … set`, `notify` and `create extension` are all transactional in Postgres, so the file either applies
completely or not at all. `cron.schedule()` is an ordinary insert into `cron.job` and rolls back with the rest.
pg_cron needs `shared_preload_libraries` (Supabase preloads it) and runs jobs in the database named by
`cron.database_name` (`postgres`, the app database) — preflight E confirms both.
