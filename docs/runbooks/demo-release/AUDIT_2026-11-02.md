# Production Supabase audit — demo migration (READ-ONLY, 2026-11-02)

Source: owner-run queries from `01_migration_audit.sql` on project `jecgmiuypuathhvjuhea`. No production change was made.

## 1. Migration history: production ≠ repository filenames

Production records **32** versions; the repository has **30** prior files + the new demo file. Only **15** versions
match by number. The other 17 production versions (`20260717191147` … `20260810014657`) carry timestamps assigned
by the Supabase MCP at apply time, while the matching repo files use hand-written versions
(`20260731090000`, `20260801120000` … `20260810020000`). The 32 vs 30 count difference means two production
entries have no single repo counterpart (most likely a repo file applied as two MCP steps, or a hotfix applied
through the MCP and folded into a later file). Mapping by *name* needs
`select version, name from supabase_migrations.schema_migrations` (names were not exported).

**Consequence:** `supabase db push` would consider 16 repo files "unapplied" and try to replay them.
**It must not be used.** The schema is already in its final state (demo objects absent, everything else present);
only the history table disagrees with the filenames.

## 2. Can the demo migration be applied on its own? Yes.

Objects it depends on, all present in production per the recorded history:

| Dependency | Where it comes from | Status |
|---|---|---|
| schema `private` | `20260716211508_extensions_and_helpers.sql` (`create schema if not exists private`) — production records `20260716211508` | present |
| `auth.users`, `auth.uid()` | Supabase built-ins | present |
| `pg_cron` | optional (see §3) | **absent** |

Everything else the file touches it creates itself (`public.demo_sessions`, `public.demo_session_status()`,
`public.paax_pre_request()`, `private.demo_cleanup()`, the role setting). The social-RPC names inside the guard are
request-path string matches; they do not require those RPCs to exist. No existing table, policy, function or RPC
is altered. Owner-confirmed pre-state: table absent, three functions absent, no pre-request hook configured on
`authenticator`. The file is therefore independent of the 16 unapplied-by-name repo files.

## 3. pg_cron is not installed — cleanup of abandoned demo identities

The migration tries `create extension if not exists pg_cron` inside a `begin … exception` block and only schedules
the sweeper if that succeeds. On Supabase the `postgres` role **can** enable `pg_cron`, so running the file as-is
**would enable an extension** — which the owner has ruled out for now. Two options:

- **A (recommended, needs a one-line approval):** allow `pg_cron` (Supabase-managed, used only for a 1-minute
  `select private.demo_cleanup();`). Cleanup is then independent of traffic. Rollback step `cron.unschedule` applies.
- **B (no extension):** apply the file **without** its final `do $$ … $$` block. Cleanup then relies on the
  paax-api backstop: `sweep_expired()` runs on every `POST /v2/demo/sessions` (grace 60 s, 20 identities per
  call). Expired identities are harmless while they linger (the guard answers 401 to every request; the JWT dies
  within 1 h), but with zero traffic they are only removed when the next visitor arrives. If B is chosen and a
  traffic-independent sweep is still wanted, the smallest addition is a periodic task inside paax-api
  (asyncio timer every few minutes calling the same `sweep_expired`); not implemented, awaits a decision.

Either way `private.demo_cleanup()` is created and can be run by hand at any time: `select private.demo_cleanup(0, 1000);`.

## 4. Compatibility, backup, rollback

- **Guard safety for real users:** returns immediately unless the JWT carries `app_metadata.paax_demo = 'true'`
  (anon, service role and all 5 real users are untouched); claim parsing is exception-wrapped; the only raises are
  the intentional PT401/PT403 for demo identities. Verified on the local stack (same Postgres 17 / PostgREST v16
  majors) with a real signup/login and reads/writes through RLS.
- **`alter role authenticator set pgrst.db_pre_request`:** standard Supabase/PostgREST mechanism, verified locally
  only. If production refuses it (privilege), the transaction below rolls everything back and nothing is attached.
- **Atomicity:** run the file inside one transaction (`begin; … commit;`). `create table/function`, `alter role`,
  `notify` and `create extension` are all transactional in Postgres, so a failure anywhere leaves production exactly
  as it is now.
- **Backup:** take a Dashboard → Database → Backups snapshot immediately before applying. Baseline to re-check after
  any rollback: `auth.users` 5, `public.profiles` 5, `public.playlists` 30.
- **Rollback:** `03_rollback_demo_guard.sql`. Step 1 (`alter role authenticator reset pgrst.db_pre_request;
  notify pgrst, 'reload config';`) removes every request-path effect within one config reload; the rest removes
  the objects and any demo identities. Tested locally.
- **History hygiene (optional, after a successful apply):** record the file so a future audit matches:
  `insert into supabase_migrations.schema_migrations(version, name) values ('20261030000000','demo_sessions');`
  (the MCP `apply_migration` tool does this automatically; the SQL editor does not).

## 5. Recommended procedure (nothing below has been run)

1. Owner decision on §3: A (allow `pg_cron`) or B (strip the `do $$ … $$` block).
2. Backup snapshot.
3. In the SQL editor, run the migration file (full for A, truncated for B) wrapped in `begin; … commit;` —
   or, with the Supabase MCP reconnected, `apply_migration` named `demo_sessions` with the same content.
4. Run `02_post_apply_checks.sql`: role config shows `pgrst.db_pre_request=public.paax_pre_request`
   (and, for A, `cron.job` lists `paax_demo_cleanup`); table and functions exist; `demo_sessions` has 0 rows.
5. Functional checks from a device: existing account login, Home, Library, one playlist; one throwaway
   registration; anon read `rest/v1/genres` with the publishable key → 200.
6. Report; only then proceed to the Cloudflare Pages stage. `DEMO_ENABLED` stays unset until stage 7.
